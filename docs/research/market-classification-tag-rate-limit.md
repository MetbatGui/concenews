# 마켓 분류 태그 조회 Rate Limit 실측

**실행일**: 2026-08-16

## 배경

Issue #23("매크로 마켓 분류")는 6 PR 로 이미 구현·merge 돼 있었으나, `MarketClassifierService.run()` 이 AC2("Gamma API 500 마켓 fetch")와 다르게 `limit=200` 을 쓰고 있었다. 이력 확인 결과 `59cb52d`(market-snapshot-collection PR #36, 무관한 작업)에서 우연히 딸려 들어간 값이었다. 500 으로 복원 전, 실제로 500 이 안전한지 재검증했다.

## 질문

마켓 목록에서 얻은 `condition_id` 마다 태그를 별도 API 콜(`GET /markets/{id}/tags`)로 조회해야 한다(Bulk 엔드포인트 없음, `LEARNINGS.md:26`). 이 콜을 500개 동시에 날려도 안전한가?

## 실측

### 1. limit=500 단발 실행 (기존 스파이크가 "안전" 이라 추정했던 시나리오)

```
fetched=476 classified=375 fetch=1.34s tags=20.58s classify=0.002s total=21.92s
```

병목은 태그 조회 구간(20.58s)이었다. `httpx.AsyncClient()` 기본 커넥션 풀(`max_connections=100`)이 원인인지 확인.

### 2. 커넥션 풀 크기 조정 — 효과 없음

| max_connections | elapsed |
|---|---|
| 100 (기본값) | 11.68s |
| 200 | 14.04s |
| 500 | 11.96s |

풀 크기는 무관했다. 서버 쪽 제한으로 판단.

### 3. 429 확인

475건 동시 요청 중:
```
200 OK: 236  /  429 Too Many Requests: 64  /  응답 없음(client timeout): 175
```

`polymarket_client.py` 기존 주석의 "500 병렬도 리밋 하회 → 안전" 은 실측이 아니라 계산 추정이었다(`LEARNINGS.md:245` — 실제 테스트는 50콜뿐, 500은 "4000/10s 예산 안" 이라는 산술 추정). `/markets` 엔드포인트의 "300 req/10s" 문서화 값이 `/tags` 엔드포인트에도 적용된다는 근거는 없었고, 실측상 `/tags` 가 더 엄격했다.

### 4. Semaphore 동시성 제한 — 명확한 개선 없음

| concurrency | elapsed | 200 | 429 | 성공률 |
|---|---|---|---|---|
| 20 | 8.58s | 217 | 260 | 46% |
| 50 | 15.43s | 297 | 180 | 62% |
| 100 | 17.40s | 347 | 130 | 73% |

동시성을 낮춰도 429 비율이 개선되지 않았다(오히려 낮은 동시성에서 실패율이 더 높았다 — 429 응답이 즉시 와서 슬롯이 빨리 비고 다음 요청이 바로 나가기 때문으로 추정).

### 5. 초당 고정 페이싱(자체 타이머) — 개선되나 여전히 부족

| per_second | elapsed | 200 | 429 | 성공률 |
|---|---|---|---|---|
| 30 | 20.08s | 420 | 57 | 88% |
| 60 | 27.37s | 441 | 36 | 92% |

`LEARNINGS.md:52` 의 "30 req/s 이하 안전" 은 `/markets` 실측이었지 `/tags` 가 아니었다 — 여기선 30 req/s 도 12% 실패한다.

### 6. limit=200 단발 실행 — 완벽

```
fetched=193 elapsed=2.49~3.33s (3회 재현) 200 OK: 193/193 (429 zero)
```

### 7. Rolling window 존재 확인

```
t=0s (200개):        193/193 성공
t=2.5s 후 (200개):    20/193 성공  ← 급락
```
```
t=0s (200개):        193/193 성공
t=30s 후 (200개):     193/193 성공  ← 완전 회복
```

Rate limit window 는 2.5초~30초 사이 어딘가로 추정된다. 실제 스케줄러 주기(`MARKET_CLASSIFIER_INTERVAL=300초`)는 이 범위보다 압도적으로 길어, 연속 재실행으로 재현한 실패 패턴은 실제 운영에서 나타나지 않는다.

## 결론

1. **클라이언트 쪽 트릭(풀 확장·Semaphore·페이싱)으로 500개 단발 처리를 안전하게 만들 수 없다.** 4가지 방식 다 시도, 전부 실패율 10%대 이상 잔존.
2. **200개는 단발로 100% 안전**하다(3회 재현).
3. **캐싱 설계(`LEARNINGS.md:293-299`)가 이미 "신규만 조회" 를 전제**하므로, 안정화 후 신규 마켓은 주기당 10~20개뿐 — 이 범위에선 어떤 방식이든 안전하다.
4. 문제는 콜드스타트(캐시 0, 신규 500개) 1회뿐이다.

## 채택한 해법

목록 조회는 `limit=500` 유지(AC2 충족, 조회 자체는 1.3초로 안 비쌈). 캐시에 없는 신규 마켓을 주기당 `NEW_MARKETS_PER_CYCLE_LIMIT=100`(실측 안전 상한 200의 절반, 여유 확보)개로 잘라 태그 조회한다. 별도 진행 상태 카운터 없이 `find_active_condition_ids` 캐시 자체가 "얼마나 진행됐는지" 를 담아, 콜드스타트가 여러 주기(최대 5회, 25분)에 걸쳐 자동 수렴한다.

## 남은 한계

`classify()` 가 `None`(UNKNOWN)을 반환하는 마켓은 캐시되지 않아 매 주기 "신규" 로 재시도된다. `LEARNINGS.md:260` 실측(100건 중 UNKNOWN 1건, 1%)상 발생 빈도가 낮아 지금은 배치 슬롯을 유의미하게 잠식하지 않을 것으로 판단했다. 다만 이번 100개 배치 제한 도입으로, UNKNOWN 마켓이 거래량 상위권에 다수 몰리는 상황이 오면 이론상 신규 마켓 처리가 지연될 수 있다 — 발생 시 재검토.
